# 练习 01 · 反向演示（30 分钟）

> 这是 10-30 口头答应过你的那次练习，当时没写成文件，现在补上。
> 目的：把你现在的「会跑 90% / 会讲 35%」拉到「会讲 70%」。

## 为什么要练这个

面试官不会让你写代码，会让你**讲**。他问「你这个项目做了什么」，
如果你只能说「我用 YOLO 训练了一个缺陷检测模型」，30 秒就结束了。

他要听的是：**输入是什么 → 中间经过什么 → 输出是什么 → 为什么这么做 → 出问题怎么查**。

所以练习的方式是：**你讲，我挑错**。不许看文档，讲不出来就是不会。

## 第一部分：口述 8 问（15 分钟）

打开电脑，对着屏幕讲，**手机录音**。讲完自己听一遍。

规则：
- 每问 **30 秒内**讲完，讲不完就是没想清楚
- 不许说「好像是」「大概」「我记得」
- 讲不出来的，写在纸上，第 8 题之后统一问

1. 从你在网页上点「开始检测」，到右边出现红框，中间发生了什么？用一句话说清。
2. 为什么要把 `.pt` 转成 `.onnx`？不转行不行？
3. 数据集为什么必须按「工件」分组划分，不能按图片随机划分？不这么做会怎样？
4. 阈值从 0.25 调到 0.60，漏检率和过杀率分别怎么变？为什么？
5. 你的模型 test 集 mAP50 是多少？为什么比 val 低那么多？你怎么向面试官解释这件事？
6. 两条命令启动整套服务，分别起的是什么？为什么必须是两条？
7. 一张图从上传到结果入库，一共写了几次硬盘？为什么这么多？
8. 产线反馈「漏检太多，客户要退货」，你第一步做什么？第二步呢？

## 第三部分：动手（5 分钟）

1. 停掉服务：`docker compose down`
2. 只起数据库：`docker compose up -d db`
3. 本机起服务（不用 Docker）：
   ```powershell
   python -m uvicorn src.service.main:app --port 8000
   ```
4. 浏览器打开 <http://127.0.0.1:8000/>，传一张**良品**图，看它判 OK 还是 NG
5. 把阈值改成 `0.05` 再传一次，看结果变不变
6. 查这次的记录：
   ```powershell
   python db\q.py "SELECT id, verdict, n_defects, latency_ms FROM inspection ORDER BY id DESC LIMIT 3"
   ```

## 答案（先自己讲，讲完再看）

<details>
<summary>1. 一句话链路</summary>

浏览器把图 POST 到 `/detect` → FastAPI 存盘并读出字节 → `detector.py` 解码、缩放到 640、归一化成张量 → ONNX Runtime 推理 → 输出在 640 画布上，按比例换算回原图坐标 → 写两条表（inspection + defect_item）→ 返回 JSON → 网页用百分比定位把框画上去。

**关键词**：归一化输入 / 坐标换算 / 两张表。
</details>

<details>
<summary>2. 为什么转 ONNX</summary>

PyTorch 推理要拖 2 GB 的运行时；ONNX Runtime 只有几十 MB，且能脱离 Python 生态、上 C++、上 ARM 板子、上 TensorRT/OpenVINO。

反直觉的一点：ONNX 文件比 .pt **更大**（11.2 MB vs 5.7 MB），因为它存的是完整计算图而不只是权重。体积不是重点，**去掉框架依赖**才是。
</details>

<details>
<summary>3. 为什么按工件分组</summary>

同一个工件的多张照片，除了微小位移几乎一样。按图片随机划分，验证集里会出现训练时见过的工件的其他角度 —— 模型相当于开卷考原题，指标虚高 15~25 个点，一上线换一批工件就崩。

按工件分组 = 闭卷考新题。代价是同样图片数量下指标更低，但那个数才是真的。
</details>

<details>
<summary>4. 阈值变化</summary>

阈值调高 → 模型要更自信才报缺陷 → **漏检率↑（更保守）、过杀率↓**。
阈值调低 → 稍微像缺陷就报 → **漏检率↓、过杀率↑**。

两者永远反向。工业上选阈值不是选「最好」，是选「客户能接受的那个组合」：汽车件宁可过杀不可漏检，包装外观反之。
</details>

<details>
<summary>5. test 为什么低</summary>

诚实答案：**42 张、7 个工件的时候 test 是 0.0037，因为模型学的是「那张纸」，不是「缺陷」**。

现在的答案：缺陷笔迹在原图约 10 像素宽，640 输入下只剩 1.6 像素，信息在缩放时就没了；换成 3 毫米马克笔、输入提到 1280、数据翻到 102 张之后才恢复。

**这道题答不好会露馅**——如果吹「我的模型 mAP 0.95」，面试官一问 test 集怎么来的就穿了。诚实 + 说清原因，反而是加分项。
</details>

<details>
<summary>6. 两条命令起什么</summary>

`docker compose up -d` 起两个容器：
- `db`：PostgreSQL，存检测记录
- `app`：FastAPI + ONNX Runtime，监听 8010，内部连 `db:5432`

必须是两条是因为 `docker compose` 一条命令就把两个都拉起来了 —— 但如果不用 Docker，就是「`pg_ctl start` 起数据库」+「`uvicorn` 起服务」两个独立进程，谁挂了另一个不会自动重启。
</details>

<details>
<summary>7. 写了几次盘</summary>

**两次**：
1. `uploads/` 存原图（要留证据、要复查）
2. PostgreSQL 写两张表 + WAL 日志

如果开了 `--reload` 或容器挂载的是 Windows 目录，第 1 次会特别慢 —— 实测绑定挂载 1219 ms，换成 Docker 命名卷降到 28 ms，整体推理从 1403 ms 降到 180 ms。**慢的不是模型，是写盘。**
</details>

<details>
<summary>8. 漏检太多怎么办</summary>

第一步 **不要动模型**，先问三个问题：
1. 漏的是哪一类缺陷？有没有共性（尺寸、位置、光照）？
2. 漏检的图人眼看得见吗？看不见 = 成像问题，先解决打光/分辨率
3. 阈值现在设的多少？先降阈值看漏检能不能下来，过杀涨多少

第二步才是看数据：这类缺陷标注了多少张？够不够？分布和产线一致吗？

**面试官要听的是「先定位再动手」，不是「我重新训练一版」。**
</details>
