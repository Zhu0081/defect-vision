# INT8 量化对比实验

日期：2026-10-29
模型：YOLO11n-seg（baseline_v1，val mAP50 0.954 / test mAP50 0.0037）
硬件：13th Gen Intel Core i5-13500HX，20 逻辑核，无独显，Windows 11
运行时：onnxruntime 1.31.1（CPUExecutionProvider），opset 13

---

## 一句话结论

**在这台机器上，INT8 量化不能让你变快；能让你不变坏。**
真正该拿走的是——量化必须配逐图验收，否则你拿到的是一个快 1.28 倍、但什么都检测不到的模型。

---

## 结果总表

| 方案 | 体积 | p50（20 线程 auto） | p50（单线程） | 判定一致率 | 平均置信度偏移 |
|---|---|---|---|---|---|
| FP32（baseline） | 11.22 MB | **32.07 ms** | 116.11 ms | — | — |
| INT8 动态量化 | 3.29 MB | 339.85 ms（0.11×） | — | — | — |
| INT8 静态·全算子 | 3.44 MB | 23.27 ms（1.28×） | — | **0/25** ❌ | 全部输出 0 |
| INT8 静态·仅 Conv | 3.43 MB | 38.42 ms（0.83×） | **94.11 ms（1.23×）** | **25/25 ✅** | 0.0087 |

体积：11.22 → 3.43 MB，**压缩 3.3 倍**（这部分是真实收益，与硬件无关）。

## 三个坑，按踩到的顺序

### 坑 1：opset 12 生成的 QDQ 节点是非法模型

```
Error Unrecognized attribute: axis for operator DequantizeLinear
```

`DequantizeLinear` 的 `axis` 属性从 **opset 13** 才存在。本项目 ONNX 是 opset 12
（当初为兼容 RKNN 选的），直接量化产出的模型 ORT 加载即失败。

**改法**：先 `onnx.version_converter` 升到 13 再量化（`ensure_opset13()`）。
**教训**：模型格式不是"导出来就行"，算子的属性随 opset 变。

### 坑 2：动态量化把 CNN 拖慢 9 倍

```
FP32        37.57 ms
INT8 动态   339.85 ms   0.11×
```

动态量化的语义是：权重预先转 INT8，激活值**推理时**临时算 min/max 再量化。
这套机制为 Transformer 的 MatMul/Gemm 设计。CNN 主体是 Conv，每个 Conv 前后
都要插一次运行时量化反量化，开销远大于省下的算力。

**教训**：动态量化 ≠ 通用加速。CNN 要用静态量化（QDQ）。

### 坑 3（最危险）：全算子静态量化快了 1.28 倍，然后输出全 0

```
FP32   该图 conf_max = 0.9632   前 3 框 [0.9632, 0.9590, 0.9500]
INT8   该图 conf_max = 0.0000   前 3 框 [0, 0, 0]
```

25 张图跑下来，**5 张有缺陷的图全部从"检出 3–6 个"变成"检出 0 个"**，
15 张良品依旧 0 个——所以"准确率"看起来还不错，判定一致率却是 80%。

原因：这个 ONNX 是 `nms=True` 导出的，置信度计算 → TopK → NonMaxSuppression
整条子图都在图内。全算子量化把分数通路也量化了，NMS 的
`score_threshold=0.25` 面对一堆解量化后为 0 的分数，直接全过滤掉。

**改法**：`op_types_to_quantize=['Conv']`，只量化卷积，其余保持 FP32。
判定一致率立刻回到 **25/25 = 100%**，置信度偏移仅 0.87%。

**教训**：**量化的风险不是变慢，是悄悄变差。**
一个只慢了 30% 但把缺陷全漏掉的模型，比原始模型危险得多——
而且如果你只测延迟、不跑精度，它看起来是"成功的优化"。

## 为什么整体没变快：线程数把 INT8 的优势吃掉了

| 线程数 | FP32 | INT8（仅 Conv） | 加速比 |
|---|---|---|---|
| 1 | 116.11 ms | 94.11 ms | **1.23×** |
| 4 | 56.45 ms | 48.55 ms | 1.16× |
| 8 | 39.89 ms | 42.75 ms | 0.93× |
| auto（20） | 32.07 ms | 38.42 ms | **0.83×** |

**线程越多，INT8 越吃亏。**

- 单线程：算力是瓶颈，INT8 的 4 倍理论吞吐能兑现一部分（实测 1.23×，
  受限于 i5-13500HX 没有 AVX-512，只有 AVX2 整数乘法）。
- 多线程：瓶颈转向内存带宽与线程调度，INT8 省的算力用不上，
  额外的 Q(D)Q 转换开销却是实打实的。

**推论（对求职最有用的一条）**：x86 + 多核 CPU 测不出 INT8 的价值。
真正的收益场景是**低功耗边缘芯片**——RK3588 的 NPU、Cortex-A76 的 dotprod 指令，
在那里 INT8 才是 2–4 倍而不是 1.2 倍。所以"在笔记本上量化"这件事的意义，
是**验证流程与精度损失**，不是验证加速比。
